The 3D field's GDScript tick is **not** the hitch. 627 ms of `_process` in
30 s is half a millisecond a frame. The leftover 73% is still CPU-side
(`draw_calls` 149 and flat, `render_objects` 412) and it is **not** vsync:
uncapped, vsync off, unaccounted is still 72%.

What is left, by elimination:

1. **The SubViewport 3D submit** — `UPDATE_ALWAYS` + MSAA 4× +
   `forward_plus` on a 2015 960M. That cost lives in RenderingServer, not in
   any `_process` we can time from GDScript. `TIME_PROCESS` last-frame
   samples still land at ~100 ms on the slow frames; our named script work
   is ~7 ms of a 26 ms mean frame.
2. **Godot's own main thread** (idle callbacks, resource pumping, the
   canvas item that composites the SubViewport).
3. A 5.5% slice we *did* name: `viz_farm_physics_rest`. Not the hitch, but
   it is the next-largest named non-native seam.

Do **not** wire `submit_lookahead_job` on this number. Moving 15% of wall
off the main thread will not remove a tail whose 73% is the 3D submit.

`buffer_state` is still `RECOVERY` for the whole window. `native_ms_per_step`
is 14.6 ms on this run (12.1 ms yesterday — this box was also exporting the
web pack during the first measurement; shares are the durable part).

## Browser — the query hook works, and then the farm dies

The page now reads the same switches as the desktop env:

    ?sw_autostart=1&sw_load_path=endrun_ending.tres&sw_perf=1

Headed Chrome, NTFS, ANGLE HD 5600 D3D11, COOP/COEP + SAB, Eigen loaded.
New export (`8cb53809-dirty`), not the rc3 pack.

| scenario | boot | rAF fps | farm started | engine report | honest verdict |
|---|---|---|---|---|---|
| title | 15.7 s | 59.8 / p95 16.8 / worst 20 | no (correct) | yes, empty attribution | **title holds 60** |
| fresh (`sw_autostart=1`) | 17.2 s | 59.9 | **aborts mid-boot** | no | **not a farm number** |
| endgame (`+ sw_load_path`) | 16.8 s | 59.9 | **aborts mid-boot** | no | **not a farm number** |

The rAF rate after the abort is a **frozen canvas**. The runner now treats
`Aborted(` / `undefined symbol` in the console tail as fatal so that 59.9
cannot be quoted as in-farm fps. The previous WEB_DOOR 59.7 / 59.8 figures
remain valid **for the title card only**.

The crash, the first time the farm actually boots in a browser:

    Aborted(Assertion failed: undefined symbol
      '_ZNSt3__213__hash_memoryEPKvm'.
      perhaps a side module was not linked in?)

That is libc++ `std::__hash_memory`. Title reaches `native acceleration
enabled (Eigen)` and sits. Autostart then enters `BOOT SESSION STARTING`
and the side module (`libquantummatrix.wasm`) asks the Godot 4.5 main
module (Emscripten 4.0.10) for a symbol it does not export. The canvas
keeps presenting; the game is dead.

This is why in-farm browser fps was never measured: every earlier headed
run stayed on the title, and rAF after an abort looks exactly like 60 fps.

### What this does to the web door

- Title / first-look: still 60 fps, 16 s boot, Eigen present. The itch
  "Play in the browser" line is honest **up to the click that starts a
  farm**.
- In-farm playable: **blocked**. Not an fps problem. A WASM ABI problem.
- Do not ship a "playable" web pack that dies on New Game until
  `libquantummatrix.wasm` is rebuilt against the same Emscripten the
  4.5 template used, or the missing libc++ symbol is stubbed / avoided.
- Soundtrack diet is still the boot-time lever (144 MB of the 175 MiB
  pck). It is not this crash.
