Complete headed investigation of the **shipping** Windows build, compared
with the same commit on Linux (no GPU, headless) and the current web pack.
Telemetry is the existing `VerboseConfig` logger (`perf` / `viz` tags) plus
the wall-clock sampler. Hitch lines look like:

`--verbose` (TRACE-everything would eat the fps we are measuring).

Build: `v0.1.0-alpha · 8cb53809-dirty · 2026-08-15`. Clock: `wall`.

main-thread physics.

### Where the named 24% actually is (endgame 3D capped)

| seam | share of 30 s wall |
|---|---|
| native `evolve_all_lookahead` | 12.7% (12.96 ms/step, 6 biomes, RECOVERY) |
| consume / refill / merge / poll | 2.4% |
| viz_field3d `_process` | 2.5% |
| viz_farm_physics_rest | 4.4% |
| viz_pgd + viz_farm | 1.5% |
| **accounted** | **23.5%** |
| unaccounted | 76.5% |

The unnamed 76% is **not** one more `_process`. Evidence:

1. 2D vs 3D (above) — renderer GDScript is 2%.
2. Linux headless (below) — **no renderer at all**, the hitch remains.
3. `TIME_PROCESS` is hitch-sticky (113 ms reported on 38/46/84 ms walls).
   It cannot be accumulated into a share; those 400%+ engine figures in
   the same JSON are the monitor lying and must not be quoted.
4. p50 is 9 ms with vsync on. After a 70 ms stall the swap chain bursts
   short frames. Those frames have almost no named work, so they inflate
   "unaccounted" without being a second cost centre.

The player-visible stall is the **packet arriving on the main thread**
(~20 ms native) plus whatever else shares that frame (physics rest, a
plot-grid refresh, Godot). Native is only 13% of wall because it is 20 Hz
and bursty, not because it is cheap when it runs.

Do not wire `submit_lookahead_job` without also measuring the 2D/headless
hitch — that is the number the async worker would actually move.

## Linux — no GPU, headless, same commit

Software / headless. `trustworthy: false` for any fps floor (`max_fps` 30,
nothing presented). Attribution is still a CPU number.

| scenario | fps (capped 30) | p95 | worst | native | field3d | note |
|---|---|---|---|---|---|---|
| title | 30.0 | 41 | 64 | 0.2% | 0 | headless autostarts a farm |
| fresh | 30.0 | 40 | 58 | 0.2% | 0 | holds the 30 cap |
| endgame | **27.9** | **106** | **224** | **7.3%** | 0 | hitch without a GPU |

`native_ms_per_step` is **7.3 ms** headless vs **13.0 ms** headed on the
same CPU. The extra 6 ms on Windows is contention with the real renderer,
not more physics. The hitch is *worse* headless (p95 106 vs 74) because
there is no GPU to hide behind and `max_fps` 30 stretches the same lumps
across fewer frames.

Conclusion: **the endgame hitch is a CPU / main-thread packet problem.**
It reproduces with no GPU and with no 3D field.

## What to do next (in order)

1. **Keep the hitch logs.** `VerboseConfig.hitch("frame"|"native_packet"|"viz_field3d")`
   is on in every sampled release. Read the 🐢 lines, not `TIME_PROCESS`.
2. **Treat the packet as the stall.** Same hitch on 2D and on headless
   Linux. The async worker is now justified by *three* independent
   measurements, not by a 3D guess. Still do not wire it until the
   unlocked-`m_node_positions` bug is closed.
3. **Do not chase MSAA / classic-2d for fps.** Four fps, not seventy.
4. **Web is a linker bug**, not an fps bug. Title is fine.

`TIME_PROCESS` accumulation is clamped in the sampler after this pass
(stale-hitch guard). Older JSON in this folder with `engine_process_share`
> 1 are the sticky monitor; ignore that field in those files.
